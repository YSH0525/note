# 출시 자동화 — 플레이 업로드를 스크립트로

AAB 업로드, 트랙 배정, 스토어 정보·이미지 갱신, 커밋까지 Google Play Developer API로
자동 처리한다. 준비가 끝나면 **태그 하나로 출시**된다.

## 최초 1회만 필요한 준비 (콘솔 작업)

API로는 **새 앱을 만들 수 없다**(구글 제약). 아래 두 가지만 해두면 이후는 전부 자동이다.

### 1. 앱 만들기

플레이 콘솔에서 앱을 하나 만든다. 패키지 이름은 반드시 `com.yoonquelabs.foldnote`.
첫 AAB는 콘솔에서 직접 올려도 되고, 아래 서비스 계정 연결을 먼저 끝냈다면 스크립트로 올려도 된다.

### 2. 서비스 계정 만들고 권한 주기

1. **Google Cloud Console** → 프로젝트 선택 → *API 및 서비스* → **Google Play Android Developer API** 사용 설정
2. *IAM 및 관리자* → **서비스 계정 만들기** → 이름 예: `foldnote-publisher`
3. 만든 서비스 계정 → *키* → **키 추가 → 새 키 만들기 → JSON** → 파일 내려받기
4. **플레이 콘솔** → *사용자 및 권한* → **초대**에 위 서비스 계정 이메일
   (`...@....iam.gserviceaccount.com`) 추가
5. 앱 권한에서 `폴드노트`를 선택하고 다음 권한을 준다
   - 앱 정보 보기
   - 프로덕션·테스트 트랙에 배포 (릴리스 관리)
   - 스토어 등록정보 관리

> 계정 권한 변경은 반영에 몇 분에서 최대 24시간까지 걸릴 수 있다. 바로 401/403이 나면 잠시 후 재시도.

### 3. 저장소에 키 등록

내려받은 JSON **파일 내용 전체**를 GitHub 저장소 시크릿에 넣는다.

```
Settings → Secrets and variables → Actions → New repository secret
  이름: PLAY_SERVICE_ACCOUNT_JSON
  값:   { "type": "service_account", ... }   ← JSON 전문 그대로
```

키 파일 자체는 저장소에 커밋하지 않는다(`.gitignore`가 `*.json` 키를 막지는 않으므로 주의).

## 출시하기

### 태그로 (권장)

```bash
git tag v1.0 && git push origin v1.0
```

내부 테스트 트랙으로 올라간다. 실기기에서 접힘/펼침 전환을 확인한 뒤 아래로 승격.

### 브랜치로 (태그 푸시 권한이 없을 때)

```bash
git push origin main:publish/v1.0             # 내부 테스트 트랙
git push origin main:publish/production/v1.0  # 프로덕션 트랙
```

브랜치 이름으로 트랙이 정해진다. Claude 세션의 토큰은 태그 푸시와 워크플로
수동 실행이 403이라 이 경로를 쓴다.

> 개인 개발자 계정은 신규 앱을 프로덕션에 올리기 전 클로즈드 테스트(테스터 12명·14일)를
> 거쳐야 하지만, **조직(비즈니스) 계정은 이 요건이 면제**되어 바로 프로덕션으로 갈 수 있다.

### 수동 실행 (트랙 선택)

GitHub **Actions → Publish to Google Play → Run workflow** 에서
트랙(internal / alpha / beta / production), 상태(completed / draft),
스토어 정보 갱신 여부, 릴리스 노트를 골라 실행한다.

### 로컬에서

```bash
# 무엇이 호출될지만 확인 (네트워크 호출 없음)
node tools/play-publish.mjs --track internal --dry-run

# 실제 업로드
export PLAY_SERVICE_ACCOUNT_JSON="$(cat ~/foldnote-publisher.json)"
node tools/play-publish.mjs --track internal --notes "첫 내부 테스트"

# 스토어 정보·이미지까지 갱신하며 프로덕션에 초안으로 올리기
node tools/play-publish.mjs --track production --status draft --listing
```

## 스크립트가 하는 일

| 단계 | API |
|------|-----|
| 편집 세션 생성 | `POST /edits` |
| AAB 업로드 | `POST /upload/.../bundles` |
| 트랙 배정 + 릴리스 노트 | `PUT /edits/{id}/tracks/{track}` |
| 스토어 정보 (`--listing`) | `PUT /edits/{id}/listings/ko-KR` |
| 이미지 교체 (`--listing`) | `DELETE` 후 `POST /upload/.../listings/ko-KR/{type}` |
| 사전 검증 | `POST /edits/{id}:validate` |
| 반영 | `POST /edits/{id}:commit` |

업로드하는 이미지 종류는 `tools/play-publish.mjs`의 `CONFIG.images`에 정의돼 있다.
폴더블 스크린샷을 7인치·10인치 슬롯 양쪽에 넣어, 대형 화면 사용자에게 펼침면이 보이게 했다.

### API 경로 함정

이미지 API는 리소스 이름이 `edits.images` 인데 **실제 URL 경로는 `/listings/`** 다.
`/images/` 로 부르면 종류를 가리지 않고 404 `Could not find handler for this request`
가 돌아온다. 권한 문제로 착각하기 쉬우니 주의. 확인 방법:

```sh
curl -s 'https://androidpublisher.googleapis.com/$discovery/rest?version=v3' > ap.json
node -e 'const m=JSON.parse(require("fs").readFileSync("ap.json","utf8"))
  .resources.edits.resources.images.methods;
  for (const [k,v] of Object.entries(m)) console.log(k, v.httpMethod, v.path)'
```

`icon`(512×512)도 이 API로 올릴 수 있다 — 핸들러가 없는 게 아니라 경로가 틀렸던 것.

### 커밋이 막힐 때 — 담은 내용을 빼가며 좁힌다

플레이는 편집 중에는 권한·유효성을 느슨하게 보고 **커밋 시점에** 한꺼번에 확인한다.
업로드가 전부 성공해도 커밋에서 막히는 이유다. 게다가 문제가 둘 이상이면
**먼저 걸린 것 하나만** 보여줘서, 그것만 고치면 다음 게 튀어나온다.

그래서 원인을 알아내는 유일한 방법은 편집에 담는 내용을 한쪽씩 빼보는 것이다.
브랜치 이름으로 조합을 고를 수 있게 해뒀다.

| 브랜치 | 편집에 담기는 것 |
|--------|-----------------|
| `publish/text*` | 스토어 문구만 |
| `publish/listing*` | 스토어 문구 + 이미지 |
| `publish/aab*` | AAB + 트랙 (draft 상태) |
| `publish/production*` | 전부 |

v1.0 출시 때 실제로 나온 대조표다.

| 편집에 담은 것 | 결과 |
|---|---|
| 아무것도 없음 | validate 통과 |
| 스토어 문구만 | **403** PERMISSION_DENIED |
| 스토어 문구 + 이미지 14장 | **403** PERMISSION_DENIED |
| AAB + 트랙(completed) | **400** `Only releases with status draft may be created on draft app.` |
| AAB + 트랙(draft) | **커밋 성공** ([run #11](https://github.com/YSH0525/note/actions/runs/31651588811)) |

여기서 세 가지가 확정됐다.

1. **아직 한 번도 게시되지 않은 앱(draft app)에는 `draft` 릴리스만 만들 수 있다.**
   첫 게시는 콘솔에서 해야 하고, 그 뒤부터 API로 `completed` 릴리스를 올릴 수 있다.
2. **출시(릴리스) 권한은 있다.** AAB + 트랙이 커밋됐으므로.
3. **스토어 등록정보 관리 권한은 없다.** 이미지를 빼고 문구만 올려도 403이므로
   특정 이미지의 문제가 아니라 등록정보 쓰기 권한 자체가 없는 것이다.

빈 편집 세션으로 시험하는 진단이 스크립트에 들어 있다(커밋이 403이면 자동 실행).
빈 편집이 커밋까지 되면 원인은 담은 내용, 빈 편집도 막히면 계정 권한 문제다.
단 **빈 편집이 통과한다고 권한이 충분하다는 뜻은 아니다** — 담긴 게 없으면 승인할 것도 없다.

`changesNotSentForReview=true` 로 심사 제출만 빼고 저장하는 우회로는 **신규 앱에는 못 쓴다.**
한 번도 출시된 적 없는 앱은 변경이 항상 자동으로 심사에 올라가서
`400 INVALID_ARGUMENT — Changes are sent for review automatically` 가 돌아온다.

## 새 버전을 낼 때

1. `app/index.html`의 `APP_VERSION`과 `android/AndroidManifest.xml`의
   `versionName`·`versionCode`를 함께 올린다 (versionCode는 반드시 증가)
2. `android/build.sh`로 AAB 재빌드 → `release/`에 넣기
3. `CONFIG.aab` 경로가 새 파일명과 맞는지 확인 (또는 `--aab` 로 지정)
4. 태그 푸시 또는 워크플로 수동 실행

## v1.0 진행 상태

`--show` 로 읽은 플레이 쪽 실제 상태 ([run #13](https://github.com/YSH0525/note/actions/runs/31652262675)):

```
[트랙]
  production: versionCode 1 · draft · 1.0
  beta / alpha / internal: (릴리스 없음)
[업로드된 번들] 1개
  versionCode 1 · sha256 b0ac8018c278c8dc…
[스토어 등록정보 ko-KR]
  제목: 폴드8노트 - 폴더블 노트·다이어리
  간단한 설명: (없음) / 자세한 설명: (없음)
[이미지] 전부 0개
```


- **완료**: 인증, 편집 세션, AAB 업로드(versionCode 1), 프로덕션 트랙에 **draft 릴리스로 커밋**
- **남음**: 스토어 등록정보(문구·이미지)와 **첫 게시**. 둘 다 콘솔에서 해야 한다
  - 등록정보는 서비스 계정에 권한이 없어 API로 못 올린다
  - 첫 게시는 draft app 제약 때문에 API로 불가능하다
- 첫 게시가 끝나면 앱이 draft 상태를 벗어나므로, 다음 버전부터는
  `git push origin main:publish/production/vX.Y` 한 줄로 끝난다

콘솔에 넣을 문구는 `store/스토어-등록-정보.md`, 이미지는 `store/` 아래에 있다.
