# 구글 플레이 신규 앱 출시 플레이북

폴드노트 v1.0을 올리며 **워크플로 13번을 돌려서** 알아낸 것을 앱에 종속되지 않게 정리한다.
다음 앱은 이 순서대로 하면 한 번에 끝난다.

> 이 문서는 특정 앱 이야기가 아니다. 새 프로젝트에 `tools/play-publish.mjs`,
> `.github/workflows/play-publish.yml`, 이 문서를 함께 복사해서 쓴다.

## 왜 13번이나 걸렸나 — 이 문서의 존재 이유

플레이는 편집(edit)을 만드는 동안에는 아무 검사도 하지 않는다. 업로드도, 트랙 배정도,
등록정보 수정도 전부 성공한다. **커밋 시점에 한꺼번에 검사하고, 문제가 여러 개여도
먼저 걸린 것 하나만 알려준다.**

그래서 이렇게 된다.

```
전부 담아서 커밋  → 403 (스토어 등록정보 권한 없음)
   권한 문제라 판단하고 헤맴 ...
스토어 정보 빼고  → 400 (draft 앱에는 draft 릴리스만 가능)   ← 가려져 있던 진짜 두 번째 문제
   status=draft 로 → 커밋 성공
```

**증상 하나에 원인 하나라고 가정하면 안 된다.** 아래 순서는 원인이 겹치지 않도록
문제를 미리 하나씩 없애는 순서다.

## 순서 (이대로 하면 막히지 않는다)

### 1. 콘솔에서 앱 만들기 — 사용자만 가능

API로는 새 앱을 만들 수 없다. 패키지 이름은 **등록 후 영원히 못 바꾸므로** 여기서 확정한다.

여기서 정한 **앱 이름을 스크립트 `CONFIG.listing.title` 에 그대로 옮겨 적는다.**
다르면 나중에 `--listing` 이 사용자가 정한 이름을 조용히 덮어쓴다.

### 2. 서비스 계정 권한 — 세 가지를 *모두* 준다

콘솔 → 사용자 및 권한 → 서비스 계정 → 앱 권한.

- 앱 정보 보기
- **릴리스 관리** (프로덕션·테스트 트랙 배포)
- **스토어 등록정보 관리**

> **둘째와 셋째는 별개다.** 하나만 있어도 편집·업로드·트랙 배정·등록정보 수정까지
> 전부 통과하고 커밋 하나만 막힌다. "거의 다 됐으니 권한은 있는 것"이라는 착각을 부른다.

권한 변경은 반영에 최대 24시간. 시간 여유를 두고 1번과 함께 먼저 해둔다.

### 3. 앱 콘텐츠 설문 — 사용자만 가능

개인정보처리방침 URL, 콘텐츠 등급, 데이터 보안, 타겟층, 광고, 앱 액세스, 정부/금융/건강.
프로덕션 출시의 필수 조건이라 어차피 해야 하고, **미리 끝내두면 원인 하나가 줄어든다.**

권한 0개로 만든 앱이면 데이터 보안은 "수집 없음"으로 답할 근거가 된다.

### 4. AAB를 draft 릴리스로 올린다

```bash
git push origin main:publish/aab/vX.Y     # --status draft, 스토어 정보 제외
```

**신규 앱(draft app)에는 `status: draft` 릴리스만 만들 수 있다.**

```
400 INVALID_ARGUMENT
Only releases with status draft may be created on draft app.
```

`completed` 로 올리면 이 오류가 난다. 스토어 정보를 같이 담으면 그쪽 오류에 가려서
이 메시지조차 못 본다. 그래서 **AAB만 따로, draft 로** 올리는 게 안전하다.

### 5. 스토어 등록정보 — API 또는 콘솔

2번 권한이 제대로 들어갔으면 API로 올라간다.

```bash
git push origin main:publish/listing/vX.Y   # 문구 + 이미지만
```

403이 나면 권한이 아직이라는 뜻이니 콘솔에서 직접 넣는다. 어차피 6번 때문에
콘솔에 들어가야 하므로 기다리는 것보다 빠를 때가 많다.

### 6. 첫 게시 — 사용자만 가능

**API에 앱 게시 메서드는 없다.** 디스커버리 문서를 전수 확인했다. 게시 상태를 바꾸는
메서드는 `appstoreappsreview.updateAppStoreHostedAppPublishStatus` 하나뿐인데
제3자 앱스토어 운영자용이라 개발자 본인 앱에는 쓸 수 없다.

콘솔에서 릴리스를 검토 후 전송한다. 이 순간 앱이 draft 상태를 벗어난다.

### 7. 이후 — 전부 자동

```bash
git push origin main:publish/production/vX.Y
```

4번의 draft 제약과 6번의 콘솔 의존이 **동시에 사라진다.** 버전 올리고 빌드하고
한 줄 푸시하면 끝이다.

## 막혔을 때 — 담은 내용을 빼가며 좁힌다

한 번에 하나씩만 알려주는 API에서 원인을 찾는 유일한 방법은 이분탐색이다.
브랜치 이름으로 편집에 담는 조합을 고르게 해뒀다.

| 브랜치 | 편집에 담기는 것 | 무엇을 가리나 |
|--------|-----------------|--------------|
| `publish/show*` | (읽기 전용) | 플레이 쪽 현재 상태 |
| `publish/text*` | 스토어 문구만 | 문구 vs 이미지 |
| `publish/listing*` | 문구 + 이미지 | 등록정보 vs 릴리스 |
| `publish/aab*` | AAB + 트랙 (draft) | 릴리스 쪽만 |
| `publish/production*` | 전부 | 실제 출시 |

실제로 이렇게 갈렸다.

| 편집에 담은 것 | 결과 | 해석 |
|---|---|---|
| 아무것도 없음 | validate 통과 | 앱 접근은 됨 |
| 스토어 문구만 | 403 | 등록정보 권한 없음 |
| 문구 + 이미지 | 403 | (같은 원인) |
| AAB + 트랙(completed) | 400 draft app | 릴리스 권한은 있음 |
| AAB + 트랙(draft) | **성공** | |

빈 편집 진단이 스크립트에 들어 있다(커밋 403이면 자동 실행). 단 **빈 편집이 통과한다고
권한이 충분하다는 뜻은 아니다** — 담긴 게 없으면 승인할 것도 없다.

## API 함정 모음

- **이미지 경로.** 리소스 이름은 `edits.images` 인데 URL은 `/listings/{language}/{imageType}` 다.
  `/images/` 로 부르면 종류를 가리지 않고 `404 Could not find handler for this request`.
  권한 문제로 착각하기 딱 좋다. `icon`(512×512)도 이 경로로 올라간다.
- **경로가 의심스러우면 디스커버리 문서를 받는다.** 추측하지 말 것.
  ```sh
  curl -s 'https://androidpublisher.googleapis.com/$discovery/rest?version=v3' > ap.json
  node -e 'const m=JSON.parse(require("fs").readFileSync("ap.json","utf8"))
    .resources.edits.resources.images.methods;
    for (const [k,v] of Object.entries(m)) console.log(k, v.httpMethod, v.path)'
  ```
- **`changesNotSentForReview=true` 는 신규 앱에 못 쓴다.** 한 번도 출시된 적 없는 앱은
  변경이 항상 자동으로 심사에 올라간다 →
  `400 Changes are sent for review automatically.`
- **오류 본문을 반드시 출력한다.** 구글은 진짜 이유를 응답 본문 JSON에 담는다.
  첫 줄만 찍으면 `→ 404` 밖에 안 남아 원인을 영영 못 찾는다.

## 출시 전 자동 점검을 붙인다

사람이 눈으로 확인하던 걸 기계가 막게 한다. `tools/preflight.mjs` 가 그 역할이고,
워크플로가 업로드 직전에 돌린다. 여기서 걸리면 배포가 진행되지 않는다.

| 검사 | 안 하면 |
|------|--------|
| 버전 문자열이 앱·매니페스트에서 일치 | 스토어 표기와 앱 안 표기가 어긋난다 |
| **업로드 대상 AAB 경로가 이번 버전을 가리킴** | **옛 번들이 올라가고 로그엔 "커밋 완료"가 찍힌다** |
| AAB에 서명이 있음 | 커밋 단계에서 거부된다 |
| 권한 개수 | 데이터 보안 설문 답변과 어긋난다 |
| 스토어 제목이 등록 문서와 일치 | `--listing` 이 콘솔의 앱 이름을 덮어쓴다 |

두 번째 항목이 제일 위험하다. **틀려도 아무 오류가 안 난다.** 업로드도 커밋도 성공하고,
스토어에 옛 버전이 그대로 남는다. 버전을 올릴 때 스크립트의 AAB 경로를 같이 고치는 걸
잊기 쉬우니 반드시 자동으로 막아야 한다.

## 안드로이드 15 엣지 투 엣지 — 웹뷰 래퍼는 거의 다 걸린다

targetSdk 35 이상이면 **시스템이 창을 화면 끝까지 강제로 늘린다.** 상태바가 내용 위에
겹쳐 그려지는데 `NoActionBar` 테마로는 안 막힌다. 실기기에 깔기 전엔 잘 안 보인다.

**CSS `env(safe-area-inset-top)` 으로 해결하려 들면 시간을 버린다.** 안드로이드 웹뷰에서
그 값은 디스플레이 컷아웃만 반영하고 **상태바 높이는 0으로 준다.** iOS와 다른 지점이라
`viewport-fit=cover` 를 이미 넣어 뒀으면 더 헷갈린다.

되는 방법은 네이티브가 실측해서 CSS 변수로 넘기는 것이다.

```java
// MainActivity implements View.OnApplyWindowInsetsListener
Insets bars = insets.getInsets(
        WindowInsets.Type.systemBars() | WindowInsets.Type.displayCutout());
float d = getResources().getDisplayMetrics().density;
web.evaluateJavascript(
    "document.documentElement.style.setProperty('--bar-top','"
    + Math.round(bars.top / d) + "px')", null);
return insets;   // 소비하지 않고 돌려준다 — 키보드(adjustResize) 동작 유지
```

- **API 35 미만에서는 아무것도 하지 않는다.** 시스템이 알아서 비켜주므로 손대면 이중으로 밀린다
- 시스템 바 높이가 페이지 로드보다 먼저 올 수 있으니 `onPageFinished` 에서 한 번 더 넣는다
- 상태바 아이콘 명암도 앱 테마에 맞춰야 한다. 바 뒤로 앱 배경이 비쳐서 밝은 배경에
  흰 아이콘이 얹히면 시계가 안 보인다 (`APPEARANCE_LIGHT_STATUS_BARS`)

## 키스토어는 임시 작업공간에 두지 않는다

Claude가 도는 컨테이너는 회수된다. 키스토어가 거기에만 있으면 **그 앱은 영영 업데이트할
수 없다.** 만든 직후 사용자에게 파일로 보내고 보관을 확인받는다. 암호도 함께 전달하되
저장소에는 절대 커밋하지 않는다 (`.gitignore` 에 `*.keystore`·`*.jks`).

서명 인증서의 SHA-256 지문을 프로젝트 문서에 적어 둔다. 다음 버전을 서명한 뒤
`keytool -printcert -jarfile <aab>` 로 대조하면 **엉뚱한 키로 서명해서 업데이트 설치가
안 되는 사고**를 올리기 전에 잡는다.

## 검증은 플레이에게 묻는다

스크립트가 "커밋 완료"를 찍는 건 **우리 출력**이다. 플레이가 실제로 뭘 갖고 있는지는
읽어봐야 안다.

```bash
git push origin main:publish/show/vX.Y
```

트랙·릴리스 상태, 번들 목록(sha256), 등록정보, 이미지 슬롯 개수를 읽는다.
편집 세션을 만들어 읽기만 하고 커밋 없이 지우므로 아무것도 바뀌지 않는다.

**AAB의 sha256을 저장소 파일과 대조하면** 콘솔에 올라간 게 우리가 빌드한 바로 그
바이너리인지까지 확인된다. 빌드 후 앱을 고쳐놓고 옛 AAB를 올리는 사고를 잡아준다.

## 새 앱에 이식하기

`tools/play-publish.mjs` 맨 위 `CONFIG` 만 고치면 된다.

```js
packageName: "com.example.newapp",   // 콘솔에서 만든 것과 동일하게
language: "ko-KR",
aab: "release/NewApp-1.0.aab",
listing: {
  title: "...",                       // 콘솔 등록명과 반드시 일치
  shortDescription: "...",            // 80자 이내
  fullDescriptionFile: "store/full-description.txt"   // 4000자 이내
}
```

워크플로는 그대로 쓴다. 저장소 시크릿 `PLAY_SERVICE_ACCOUNT_JSON` 만 새로 등록하면 된다
(서비스 계정은 여러 앱에 재사용할 수 있고, 앱마다 권한만 따로 준다).

## 이미지 규격

| 종류 | 규격 | 개수 |
|------|------|------|
| `icon` | 512×512 PNG | 1 |
| `featureGraphic` | 1024×500 | 1 |
| `phoneScreenshots` | 세로형, 짧은 변 320px 이상 | 2~8 |
| `sevenInchScreenshots` · `tenInchScreenshots` | 태블릿/대화면 | 각 2~8 |

폴더블 앱이라면 펼침면 스크린샷을 7인치·10인치 슬롯 **양쪽에** 넣는다.
대화면 사용자에게 펼친 모습이 보인다.

## Claude가 할 수 없는 것

격리된 클라우드 컨테이너에서 돌기 때문에 브라우저로 콘솔에 접속할 수 없다.
로그인해 두셔도 그 세션을 쓸 수 없다.

- 콘솔에서 앱 생성 · 첫 게시 · 앱 콘텐츠 설문 · 서비스 계정 권한 부여
- 저장소 시크릿 등록
- 태그 푸시와 `workflow_dispatch` (세션 토큰이 403) → `publish/**` 브랜치 푸시로 대신한다

**우회로 — 콘솔 화면은 브라우저 에이전트에게 시킨다.** 크롬 확장에 붙여넣을 프롬프트를
[콘솔-점검-프롬프트.md](콘솔-점검-프롬프트.md) 에 정리해 뒀다. 관리형 게시 여부·정책
경고·릴리스 상태처럼 API에 없는 정보를 읽어온다. **금지 버튼 목록을 프롬프트 맨 앞에
두어 읽기 전용으로 묶는 것**이 핵심이다 — 콘솔의 파괴적 동작은 되돌릴 수 없다.
